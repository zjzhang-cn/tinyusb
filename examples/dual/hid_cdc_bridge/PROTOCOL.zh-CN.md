# CDC 通讯协议（hid_cdc_bridge）

本文描述 `examples/dual/hid_cdc_bridge` 在 **CDC 口（USB2，端口 1 / USBFS）** 上的
二进制通讯协议：主机通过它把键盘、指针、系统键注入到 HID 口（USB1，端口 0 / FSDev）
所连的目标机器，设备反过来通过同一链路上报状态。

帧格式与上一代 ESP32 产品保持一致：键盘（`0x8257`）与绝对鼠标（`0x8357`）连 header
和 tail 都未改动；`0x8557`、`0x8657`、`0x8757`、`0x8758` 为新增。上一代还有一个
**纯按键帧 `0x8457`，已移除**：鼠标帧本来就携带按键位图，点击可以走相对指针的零位移帧
（不需要坐标），也可以走绝对指针重复坐标（见 3.4）；旧主机若继续发 `0x8457`，只会丢掉
这一次点击，不会误动作。

- 英文说明：[README.md](README.md)
- 参考实现：`src/bridge_protocol.h`（帧定义）、`src/main.c`（语义）、`src/usbfs_cdc.c`（链路）
- 主机工具：`tools/bridge_check.py`（验收测试）、`tools/cdc_tui.py`（交互调试）

## 1. 链路

### 1.1 USB 设备

| 项目 | 值 |
|---|---|
| VID:PID | `cafe:4001` |
| 产品名 / 厂商 / 序列号 | `CDC Bridge` / `TinyUSB` / `203C10002` |
| 设备类 | `0x02`（CDC），bcdUSB 1.10，bcdDevice 0x0100 |
| 配置 | 1 个配置，2 个接口，总线供电 100 mA（`bMaxPower` 0x32） |
| 接口 0 | CDC 通信类（ACM），含功能描述符 |
| 接口 1 | CDC 数据类，2 个 bulk 端点 |

### 1.2 端点

| 端点 | 方向 | 类型 | 包长 | 轮询 | 用途 |
|---|---|---|---|---|---|
| `0x00` / `0x80` | 双向 | 控制 | 64 | — | 枚举、CDC 类请求 |
| `0x81` | IN | 中断 | 16 | 1 ms | 通知端点（开着、被应答，但设备从不排队数据） |
| `0x02` | OUT | 批量 | 64 | — | 主机 → 设备（帧输入） |
| `0x82` | IN | 批量 | 64 | — | 设备 → 主机（状态帧） |

> 端口 1 的数据 IN 用 **EP2**（与 OUT 复用 EP2，DCD 已支持双向）：这颗芯片上 EP3 的
> IN 通路不可靠。

### 1.3 串口参数与握手线

- `SET_LINE_CODING` 保存 7 字节线路编码，默认 **115200 8N1**；它只用于 `GET_LINE_CODING`
  回读，链路是 USB 批量传输，**不按波特率限速**。
- `SET_CONTROL_LINE_STATE` 的 bit0（DTR）、bit1（RTS）被记录，并作为状态帧的
  `flags` 上报（线状态变化会触发一帧）。两者都**不参与门控**：主机不置 DTR/RTS
  也照常收发。
- **CTS 不上报**：该请求没有供设备读取的 CTS 位，`SERIAL_STATE` 通知里也没有，Linux
  的 `cdc_acm` 直接硬编码 `TIOCM_CTS`，因此报一个 CTS 位没有意义。
- 设备**不发送 `SERIAL_STATE` 通知**，主机不要等待它。

### 1.4 主机侧要求

链路是二进制帧，主机必须把 tty 置为 **raw 模式**：

- 关闭 `ICANON`（否则 `read()` 只在行分隔符返回，一帧 12 字节几乎永远不含换行，
  表现为“出一段就卡死”）；
- 关闭 `ICRNL`/`OPOST`（否则 `0x0D` 会被改写为 `0x0A`，帧内容被破坏）；
- 关闭 `IXON`/`IXOFF`/`CRTSCTS`（建议；实测主要症结是 `ICANON`）。

```python
import tty, termios

tty.setraw(fd)                                   # 无 ICANON / ICRNL / OPOST
attrs = termios.tcgetattr(fd)
attrs[2] &= ~termios.CRTSCTS
attrs[0] &= ~(termios.IXON | termios.IXOFF)
termios.tcsetattr(fd, termios.TCSANOW, attrs)
```

`tools/bridge_check.py` 与 `tools/cdc_tui.py` 已按此设置。

## 2. 帧格式

### 2.1 通用结构

固定 **12 字节**，多字节字段一律 **小端**：

| 偏移 | 长度 | 类型 | 含义 |
|---|---|---|---|
| 0 | 2 | u16 | header，见 2.2 |
| 2 | 8 | u8[8] | payload，按帧类型解释 |
| 10 | 2 | u16 | tail，固定 `0x0900`（线上字节 `00 09`） |

- 帧之间没有间隔、没有长度字段：一个 USB 包的边界与帧边界无关，解析器按**字节流**处理。
- 一次 `write` 可以包含多帧，一帧也可以跨多次写入。

### 2.2 帧类型

| header | 线上的两个字节 | 方向 | 含义 | 引入 |
|---|---|---|---|---|
| `0x8257` | `57 82` | 主机 → 设备 | 键盘 | 原有 |
| `0x8357` | `57 83` | 主机 → 设备 | 鼠标（绝对），含按键位图 | 原有 |
| `0x8557` | `57 85` | 主机 → 设备 | 鼠标移动（相对），含按键位图 | 新增 |
| `0x8657` | `57 86` | 主机 → 设备 | 系统键 | 新增 |
| `0x8758` | `58 87` | 主机 → 设备 | 状态查询 | 新增 |
| `0x8757` | `57 87` | 设备 → 主机 | 状态上报 | 新增 |

- 设备解析器只接受上表中**主机 → 设备**的 header；`0x8757` 不会被当作输入帧。
- `0x8457`（纯按键帧）已移除，现在属于未知 header：发出的点击帧会被丢弃并触发一次重同步。
- 未知 header 视为噪声：丢弃 1 字节后重新同步（见 4.1）。

## 3. 各帧定义

### 3.1 键盘 `0x8257`

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | u8 | 修饰键位图，见下表 |
| 1 | u8 | 保留，**必须为 0**（会原样进入 HID 报告的保留字节） |
| 2…7 | u8[6] | HID 键盘 usage，0 表示空槽 |

修饰键位图（HID 规范）：

| bit | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 键 | 左 Ctrl | 左 Shift | 左 Alt | 左 GUI | 右 Ctrl | 右 Shift | 右 Alt | 右 GUI |

语义：

- **整帧替换**：帧到达后设备的按键集合就被这 8 字节整体取代，不做增量合并。
- **不自动重复、不自动松开**：按下发 usage，松开必须显式再发一帧（全 0 即全部松开）。
- 最多 6 键同时按下（6KRO），不支持 NKRO。
- 不去重：重复发送同一状态也会再发一个 HID 报告。

### 3.2 鼠标类帧共用的 payload（`0x8357` / `0x8557`）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | u8 | 按键位图 |
| 1 | i8 | 保留，必须为 0 |
| 2…3 | i16 | X（绝对坐标或增量，取决于 header） |
| 4…5 | i16 | Y（同上） |
| 6 | i8 | wheel（垂直滚轮），**增量** |
| 7 | i8 | pan（水平滚轮），**增量** |

按键位图（与 HID 报告一致，HID 描述符声明 5 个按键）：

| bit | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 键 | 左键 | 右键 | 中键 | 后退 | 前进 |

协议只定义前三个；`bit3`/`bit4` 会原样传给目标机，工具未使用。

### 3.3 绝对鼠标移动 `0x8357`

- 字段是 signed 16 位，有效范围 **0…4096**，映射到 HID 报告的 0…32767：`≤0 → 0`，
  `≥4096 → 32767`，其余 `×8`。注意 4096 映射到 32767 而不是 32768。
- **覆盖语义**：位置不是累加，一帧直接设定新位置；突发多帧时只有最后一帧的坐标
  会被发出（中间位置被合并丢弃）。
- **仅滚轮帧**：`X` 与 `Y` 都为 0、但 `wheel`/`pan` 非 0 时，视为“只滚轮”，
  保留上一次位置——否则绝对指针会每次滚动都跳到左上角。
- **点击**见 3.4：不知道坐标时用 `0x8557` 的零位移帧；用 `0x8357` 则 `X`、`Y` 必须填
  上次发送的值，否则指针会跳到左上角。
- `wheel`/`pan` 是增量：多帧可合并进一个报告（1 ms 间隔），累加并饱和到 ±127，
  报告真正发出后清零。
- 上一代 ESP32 固件在线上也带这两个字节，但描述符里没有滚轮用途，滚轮从未生效。

### 3.4 点击：两种表达

协议没有独立的按键帧（`0x8457` 已移除），按键位图随每个鼠标帧一起送达，因此点击有两种写法：

| 路径 | 帧 | 适用 | 落在哪个输入设备 |
|---|---|---|---|
| 相对指针（推荐） | 两帧 `0x8557`，`dx = dy = 0`，只改 `buttons` | **不知道绝对坐标**，或光标由目标 OS 自己移动 | 接口 1（Mouse REL） |
| 绝对指针 | 两帧 `0x8357`，`X`/`Y` 重复上一次的值，只改 `buttons` | 主机自己维护绝对坐标 | 接口 0（Mouse ABS） |

**相对指针路径（零位移帧）**：

- 例：按下 `57 85 01 00 00 00 00 00 00 00 00 09`，松开
  `57 85 00 00 00 00 00 00 00 00 00 09`。
- 不需要坐标：光标停在目标 OS 当前位置，主机重启、或从未发过 `0x8357` 都不会跳角。
- 零位移帧仍会产生一个 HID 报告（`rel_state.dirty` 由按键变化置位），所以按下、松开都能送达。

**绝对指针路径**：

- `X`、`Y` 必须填**设备当前的绝对坐标**（上一次成功发出 `0x8357` 时的原值）；重复同一坐标
  不产生位移事件，点击就落在原处。
- 不知道坐标时不要用这条：填 0 是把指针送到左上角，不是“保持不动”。设备初始坐标是
  `(0,0)`，之后只由 `0x8357` 改写，`0x8557` 不会改变它。

**两条路径共同点**：

- 按下与松开必须落在**同一个输入设备**：两套指针的按钮状态各自独立，混用（按下走
  `0x8357`、松开走 `0x8557`）会在目标机上留下按住的键。
- 若此前还有未发出的 `wheel`/`pan` 增量，它们会随本次报告一起发出并清零。
- 点击 = 按下帧 + 松开帧；拖拽 = 按下 → 多次带 `buttons` 的移动帧 → 松开（全程同一台
  指针设备）。

### 3.5 相对鼠标移动 `0x8557`

- `X`/`Y` 是**增量**（设备单位），目标 OS 自己移动光标；与绝对指针互不影响。
- 增量跨帧**累加**（饱和到 ±32767），每个 HID 报告每轴最多 ±127，余量留到下一个
  1 ms 报告，因此主机发得比 1 kHz 快也不丢位移。
- `wheel`/`pan` 同样累加、饱和 ±127、发完清零。
- 相对指针位于**第二个 HID 接口**：Linux `hid-input` 会忽略同一设备上重复的 HID
  用途，而绝对集合已经占用了 `Wheel(0x38)`，两者放同一接口会让相对滚轮静默失效；
  分开后系统键也获得了独立的输入设备。

### 3.6 系统键 `0x8657`

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | u8 | `0` 释放，`1` 电源（power down），`2` 睡眠，`3` 唤醒 |
| 1…7 | u8 | 保留，0 |

- 系统键是**瞬时键**：固件发出按下报告，并在下一个毫秒自动发释放报告，主机**只需发
  一次 `code`**，不必自己跟踪松开。
- `code > 3` 被忽略；`code = 0` 用于主动取消挂起的按下。
- 若 HID 总线处于挂起状态，有待发报告时固件会 `tud_remote_wakeup()`（前提是目标主机
  在配置时允许远程唤醒）；唤醒键本身也会作为按键送达。

### 3.7 状态查询 `0x8758`（主机 → 设备）

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | 2 | header `0x8758`（线上 `58 87`） |
| 2 | 1 | token，设备在状态帧里原样回显 |
| 3…9 | u8 | 填充，0 |
| 10 | 2 | tail `0x0900` |

设备收到后立即置“待上报”标志，在下一轮循环发出状态帧，`token` 原样带回，主机据此
把应答和请求对应起来、并发现丢帧（实测往返约 0.1 ms）。

### 3.8 状态帧 `0x8757`（设备 → 主机）

只承载状态，不发任何输入。

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | 2 | header `0x8757`（线上 `57 87`） |
| 2 | 1 | 状态：`0` 未挂载，`1` 活动，`2` 挂起 |
| 3 | 1 | 已配置的 HID 接口数（0 或 2） |
| 4 | 2 | 生成该帧时的 uptime（秒，约 18.2 h 回绕） |
| 6 | 1 | flags：bit0 = DTR，bit1 = RTS（主机设置的原值） |
| 7 | 1 | 键盘 LED 位图 |
| 8 | 1 | token，回显查询 |
| 9 | 1 | 保留，0 |
| 10 | 2 | tail `0x0900` |

`flags`：

- bit0 = DTR，bit1 = RTS，均为主机在 `SET_CONTROL_LINE_STATE` 里设置的值；
- 只做信息上报，任何一位都不影响收发。

`leds`（HID LED 页，由主机发来的输出报告得到）：

| bit | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 含义 | Num Lock | Caps Lock | Scroll Lock | Compose | Kana |

目标主机还没发过 LED 输出报告时，设备并不知道灯态，该字节为 0。

上报时机（**事件驱动，无心跳**）：

1. HID 口挂载 / 卸载 / 总线挂起 / 恢复；
2. 键盘 LED 位图变化（含挂载后主机发来的第一份输出报告）；
3. DTR 或 RTS 变化（打开/关闭端口即 DTR 边沿）；
4. CDC 口首次枚举完成（设备启动后的第一帧；此时主机往往还没置 DTR，`flags` 为 0，随后 DTR 置位会再触发一帧）；
5. 收到 `0x8758` 查询。

因此：

- 链路安静是正常的，`uptime` 是“最近一次事件的时刻”，**不是**心跳计数；
- 主机想知道当前状态就发查询；
- 设备只在 CDC 口已枚举时发送状态帧；
- 打开端口只会得到 1 帧，空闲 7 s 一帧都没有，每次 DTR/RTS 边沿和每次查询各 1 帧。

## 4. 设备端处理语义

### 4.1 解析与重同步

解析器是逐字节状态机（`src/bridge_protocol.c`）：

1. 只要缓冲 ≥2 字节就取前 2 字节作 header；
2. header 不在白名单 → 丢掉最旧的 1 字节，重试；
3. 不足 12 字节 → 等待后续字节；
4. 第 10–11 字节不是 `00 09` → 丢掉最旧的 1 字节，重试；
5. 校验通过 → 解析出事件，缓冲清空。

结论：丢字节、插噪声最多损失**一帧**；误判需要 header 恰好命中白名单且第 10–11
字节恰为 `00 09`，概率极低。

### 4.2 合并与发送节拍

- HID 中断端点 1 ms 轮询；主循环每轮对**接口 1** 和**接口 0**各最多发 1 个报告。
- 发送顺序：系统键、相对指针（接口 1）→ 键盘、绝对指针（接口 0）。
- 键盘与绝对位置是**状态覆盖**（后到的帧生效）；相对位移与两种滚轮是**累加**。
- 系统键按下后，释放报告在下一轮发送。

### 4.3 缓冲与背压

| 缓冲 | 大小 | 满了怎么办 |
|---|---|---|
| CDC 接收环（主机 → 设备） | 256 B | 丢弃该 USB 包剩余字节 |
| CDC 发送环（状态帧） | 128 B | 本轮写入失败，下一轮重试 |

- IN 传输按“装填 → 等完成”串行化，绝不在传输进行中重新装填；
- 12 字节状态帧对 64 字节端点而言是**短包**，控制器要等主机再发一个 IN token 才报告
  完成，因此 1 s 安全阀只用于“主机彻底不读”的情况（超时后复位端点重新同步）；
- 主机以 raw 模式读取时一帧几毫秒完成，安全阀不会触发。

## 5. 与 HID 报告的映射

| 帧 | 接口 | 报告 ID | 报告内容（不含 ID） | 长度 | 端点 |
|---|---|---|---|---|---|
| `0x8257` 键盘 | 0 | 1 | modifier, reserved, keycode[6] | 8 | `0x81` |
| `0x8357` 绝对移动 | 0 | 2 | buttons, x(2), y(2), wheel, pan | 7 | `0x81` |
| `0x8357` 点击（同坐标，仅改 buttons） | 0 | 2 | 同上，坐标不变 | 7 | `0x81` |
| `0x8557` 相对移动 | 1 | 3 | buttons, dx, dy, wheel, pan | 5 | `0x82` |
| `0x8557` 点击（零位移） | 1 | 3 | 同上，dx=dy=0 | 5 | `0x82` |
| `0x8657` 系统键 | 1 | 4 | code | 1 | `0x82` |

- 绝对报告：5 键 + 3 位填充，X/Y 为 16 位绝对值 0…32767，滚轮/横向滚轮 8 位相对量；
- 相对报告：5 键 + 3 位填充，X/Y/滚轮 8 位相对量（横向滚轮在 Consumer 页用
  `AC Pan`）；
- 键盘报告：8 位修饰键 + 8 位保留 + 6 个键码；
- 目标机上会出现 4 个输入设备：Keyboard、Mouse（ABS）、Mouse（REL）、System Control。

## 6. 示例帧

每行 12 字节，十六进制，`header | payload[8] | tail`。

| 动作 | 字节 |
|---|---|
| 键盘按下 `a`（usage 0x04） | `57 82 00 00 04 00 00 00 00 00 00 09` |
| 键盘按下 `A`（左 Shift + 0x04） | `57 82 02 00 04 00 00 00 00 00 00 09` |
| 键盘全部松开 | `57 82 00 00 00 00 00 00 00 00 00 09` |
| 绝对移动到 `2048,2048` | `57 83 00 00 00 08 00 08 00 00 00 09` |
| 绝对位置不动，滚轮 +1 | `57 83 00 00 00 00 00 00 01 00 00 09` |
| 左键按下（原地，绝对指针，坐标 2048,2048） | `57 83 01 00 00 08 00 08 00 00 00 09` |
| 左键松开（同一坐标） | `57 83 00 00 00 08 00 08 00 00 00 09` |
| 右键按下（同一坐标） | `57 83 02 00 00 08 00 08 00 00 00 09` |
| 左键按下（相对指针，无需坐标） | `57 85 01 00 00 00 00 00 00 00 00 09` |
| 左键松开（相对指针） | `57 85 00 00 00 00 00 00 00 00 00 09` |
| 相对移动 `+10,-5` | `57 85 00 00 0A 00 FB FF 00 00 00 09` |
| 相对滚轮 `+1` | `57 85 00 00 00 00 00 00 01 00 00 09` |

## 7. 主机端参考实现（Python）

```python
import struct

FRAME = struct.Struct("<H8sH")   # header, payload[8], tail
TAIL = 0x0900

HDR_KEYBOARD   = 0x8257
HDR_MOUSE_ABS  = 0x8357
HDR_MOUSE_REL  = 0x8557
HDR_SYSTEM     = 0x8657
HDR_STATUS     = 0x8757
HDR_STATUS_REQ = 0x8758


def frame(header, payload):
    """payload 必须正好 8 字节"""
    return FRAME.pack(header, payload, TAIL)


def keyboard(modifier, keycodes):
    keys = bytes(keycodes) + bytes(6 - len(keycodes))
    return frame(HDR_KEYBOARD, bytes([modifier, 0]) + keys)


def mouse(header, buttons, x_or_dx, y_or_dy, wheel=0, pan=0):
    return frame(header, struct.pack("<Bbhhbb", buttons, 0,
                                     x_or_dx, y_or_dy, wheel, pan))


def click_press(buttons, x, y):
    """x/y 必须是设备当前的绝对坐标（上一次 0x8357 发出去的值）"""
    return mouse(HDR_MOUSE_ABS, buttons, x, y)


def click_release(x, y):
    return mouse(HDR_MOUSE_ABS, 0, x, y)


def click_rel(buttons):
    """相对指针点击：不需要坐标，按下/松开都是零位移帧"""
    return mouse(HDR_MOUSE_REL, buttons, 0, 0)


def system_key(code):          # 0 释放, 1 电源, 2 睡眠, 3 唤醒
    return frame(HDR_SYSTEM, bytes([code]) + bytes(7))


def status_query(token=0x00):
    return frame(HDR_STATUS_REQ, bytes([token]) + bytes(7))
```

解析方向（状态帧）同样是 12 字节定长，用“header + tail 双校验”后取 payload：

```python
def parse_status(buf):
    if len(buf) < 12:
        return None
    header, payload, tail = FRAME.unpack_from(buf)
    if header != HDR_STATUS or tail != TAIL:
        return None
    state, itfs, uptime, flags, leds, token, _ = struct.unpack("<BBHBBBB", payload)
    return {"state": state, "itfs": itfs, "uptime": uptime,
            "dtr": bool(flags & 1), "rts": bool(flags & 2),
            "leds": leds, "token": token}
```

## 8. 排错对照

| 现象 | 原因 | 处理 |
|---|---|---|
| 打开端口后只收到 1 帧，之后安静 | 设计如此（事件驱动、无心跳） | 需要状态就发 `0x8758` |
| 读一会儿就“卡死”，`cat /dev/ttyACM*` 出一段即停 | tty 处于 canonical 模式 | 置 raw（`tty.setraw`） |
| 帧内容错位、`0x0D` 变成 `0x0A` | `ICRNL`/`OPOST` 未关 | 同上，raw 模式 |
| 每次滚轮指针跳到左上角 | 发了 `X=Y=0` 的 `0x8357`（不是“仅滚轮”帧） | 滚轮帧必须带非 0 的 `wheel`/`pan`，或改用 `0x8557` |
| 点击后指针跳到左上角 | 绝对点击帧的 `X`、`Y` 填了 0 | 填上次发送的坐标，或改用 `0x8557` 零位移帧（见 3.4） |
| 不知道绝对坐标时没法点击 | 绝对帧必须带坐标 | 用 `0x8557` 的零位移帧点击，它不需要位置（见 3.4） |
| 旧主机点击无效 | 它发的 `0x8457` 已移除，按噪声丢弃 | 改发点击帧：`0x8557` 零位移或 `0x8357` 带坐标（见 3.4） |
| 相对滚轮无效 | 两个指针集合放在同一 HID 接口会丢用途 | 已分接口；确认目标机识别到 Mouse (REL) |
| 按键“粘住” | 只发了按下帧 | 松开必须显式发（`0x8257` 全 0） |
| 系统键没反应 | `code` 越界，或目标 OS 不接受该键 | `code` 只能 1…3；目标机需支持 KEY_POWER/KEY_SLEEP/KEY_WAKEUP |
| 挂起的目标机没有被唤醒 | 目标未启用远程唤醒 | 主机侧允许 wakeup；固件据此调用 `tud_remote_wakeup()` |
| `uptime` 突然变小 | 16 位秒计数 18.2 h 回绕 | 正常 |
| 状态帧偶尔丢 | 发送环满或主机不读 | 设备下一轮重试；主机连续读 |

## 9. 兼容性

| 项 | 结论 |
|---|---|
| `0x8257` / `0x8357` 与 tail `0x0900` | 与 ESP32 产品字节一致，旧主机的键盘与鼠标移动无需修改 |
| `0x8457` 纯按键帧 | **已移除**：旧主机发出的点击会被当作噪声丢弃（最多损失 1 帧），需改成 `0x8557` 零位移帧或带坐标的 `0x8357` |
| `0x8557`/`0x8657` | 新增方向；旧主机不发，设备也无副作用 |
| `0x8757`/`0x8758` | 新增反向上报；旧主机不解析、也不查询，链路保持安静 |
| `flags` bit1（RTS） | 新增；只读 bit0 的旧主机不受影响 |
| `leds` bit3/bit4 | 新增（Compose/Kana）；旧主机按 bit0..2 解析不受影响 |
| 保留字段 | 协议不校验，但会原样传给 HID 报告，**建议一律填 0** |
| 未知 header | 当作噪声丢弃（最多损失 1 帧），不会导致链路失步 |
